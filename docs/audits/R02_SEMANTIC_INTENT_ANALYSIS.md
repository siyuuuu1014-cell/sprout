# R02 enhancement: bounded LLM semantic ambiguity analysis

Baseline: `1680cac6bbcb3a0df1c6e9ebc2aa2f7d50d93c75`.
Branch: `codex/r02-intent-clarification`. Local, uncommitted review material.
This extends, rather than replaces, the durable clarification feature. Historical
reports in `R02_INTENT_CLARIFICATION.md` retain their original test scope.

## Routing and authority

Both Runtime handle paths perform entry filtering and Session ownership checks
first. Exact pending selections and conservative rules retain their fast path.
An unfamiliar pending answer uses the same classifier, with only bounded owned
recent Turns and the saved question. A new topic may supersede the old question;
its classification is passed forward in a request-local server dictionary.
It is never cached in client Message metadata or global Runtime state.

For a normal message the existing context/classification call now also produces
semantic candidates. Before publishing intent events or dispatching the Agent,
the semantic router compares the validated candidates' action modes. The same
classification is then reused by `_recognize_intent`, if clarification is not
needed. No second classifier request is made for that input. The eight Intent
values and canonical event mapping remain unchanged, including strategy.

Model analysis itself has no tool, workspace or task handles. A material ambiguity
issues a durable question, not a task event, Workspace Consent or coding Task.
Unknown identity or an unsupported store cannot gain clarification eligibility.

## Structured model protocol v1

The exact top-level fields are `intent`, `confidence`, `reason`, `semantic`.
`semantic` has exactly:

- `version`: integer 1 (not boolean).
- `action_mode`: conversation, read_only_analysis, code_modification,
  tool_execution, or uncertain.
- `candidates`: one to four unique `{intent, action_mode}` pairs; intent uses the
  existing eight-value enum.
- `ambiguity_type`: none, read_vs_write, discuss_vs_execute, view_vs_tool,
  or missing_scope.
- `missing_information`: up to four unique requested_action, target, scope,
  whether_modification_is_requested entries.
- `needs_clarification`: boolean advice, not the final decision.
- `question`: bounded model suggestion, not displayed/executed verbatim.
- `answer_choice`: read, write, chat, cancel, unclear, or new_topic.
- `answer_evidence`: an exact quote from the current answer, not history.

Strict JSON rejects duplicate/unknown/missing fields, wrong types/enums,
NaN/infinity, out-of-range confidence, oversized strings/candidate lists and
deeply recursive input. Response limit is 12,000 characters; reason/question/
evidence limits are 400/240/500. Parsing does not repair semantic JSON fences.
Legacy classifier JSON remains a routing-only compatibility fallback: arbitrary
fields and raw model reasons are discarded and never become semantic evidence.
Returned tool calls are never executed by the classifier.

## Deterministic adjudication

Existing explicit-write and known-nonwrite rules take precedence; simple greetings
and exact ordinary assent/read/chat/cancel choices are not semantic ambiguity.
For UNKNOWN text, code compares actual candidate action modes and ambiguity kind:
read versus code, discussion versus effects, information versus tools, or missing
target/scope for an effectful interpretation. Confidence is not consulted.
The model's advice flag cannot negate a material difference in candidate effects.
Questions are generated by server templates, not model instructions.

Code-modification choices can only ask the original independent Workspace
Consent. Tool-only or missing-scope questions freeze a nonwrite choice subset
and require a fresh complete request for an operation. SQL rejects attempts to
resolve a disallowed write choice, even if the Python router is bypassed.

Exact answers retain their zero-classifier-call path. Conservative long-form
read/chat/cancel and explicit modification phrases have a local fast path.
Novel answers may use the model's selection plus exact evidence. Write requires
an independently validated explicit request speech act, with full-text negation/
quotation guards; generic assent cannot become write by quoting itself. Unsupported
wording or invalid semantic output repeats the pending question rather than
guessing a write selection. This is intentionally not unrestricted NLU coverage.

## Persistence and failure compatibility

No new database schema is introduced by this semantic extension. Existing
`choices_json` freezes the server-selected subset; its default four choices and
old v1 records remain compatible. The optional store issuance keyword is additive.
Existing conditional resolution, cross-record answer receipts, frozen Principal,
content hashes, TTL, conflict blocking and exact-ID Consent recovery remain in use.
There is no history adoption, proof upgrade, automatic replay or process-only lock.
No real user database was opened or migrated.

Write selection remains intent, not authorization. Workspace Consent, task
permissions, ChangeProposal verification and Apply approvals remain unchanged.
Read responses retain the explicit disclosure that no repository was inspected.

## Calls, privacy and configuration

```toml
[runtime]
intent_semantics_enabled = true
intent_semantics_timeout_seconds = 5.0
```

This is server configuration, not message metadata. Disabling semantics preserves
the older classifier and rule clarification; unsupported semantic-only answers
remain unresolved. Each dispatch invokes the classifier provider at most once,
without application-level retries, with an asynchronous timeout clamped to
0.01..30 seconds. Exact write requests/rule questions/exact selections do not
need a classifier call. Selecting read may additionally use the pre-existing,
separate model-only response-generation call. A provider may have its own shared
fallback/retry/output-token policy; this layer is not a global billing hard cap.

Classifier payloads omit raw metadata, identities, roles, credentials, workspace
paths and memory metadata. Recent conversation is bounded to six 500-character
items; pending-answer classification uses at most four owned Turns. Existing
similar-context retrieval is retained, but only bounded weighted text/score fields
are sent, without session IDs or hashes. The existing Redactor scrubs credential
patterns before model input. This is data minimization, not a proof that arbitrary
natural-language text contains no private information. No raw model reason or
question is logged/published: telemetry uses fixed outcome, provider-call count
and latency only. Model/provider availability and quality remain deployment risks.

## Final review correction: selection target and prompt agreement

The initial 36-case review reproduced 19 failures / 17 passes (Python 1) under
`semantic-scope-red/`: long answer parsing could apply a different object's
request to the old goal, and the semantic-enabled User Prompt still showed the
legacy example. Evidence remains outside Git beside the earlier test runs.

Long read/write selections now compare literal target evidence against the
frozen request before consumption. The bounded request grammar strips generic
object kinds, not domain names; there is no login/cache entity table, fuzzy name
matching, model-supplied identity or implicit translation authority. Same literal
names retain the existing selection route. Explicit different names supersede
the old clarification. A new explicit write request asks separate Workspace
Consent for its actual input, without the old clarification link; it does not
open a workspace or create a task. Unproved or deictic object references keep
the old record pending without consumption or a write event. Supported complete
target-free selections retain their existing meaning. Unknown aliases and
cross-language name equivalence are not guessed; an explicit differently named
command is treated as a fresh request rather than rewriting the old goal.

Semantic-enabled System/User prompts now require a complete four-field response
and provide a fully validated v1 example. Disabled mode explicitly retains the
three-field contract. The existing Input JSON boundary and eight-intent mapping
are unchanged. No Schema or approval semantics change is part of this correction.

The targeted green run recorded 175 passed, no failures/errors/skips, Python 0
(`semantic-scope-green-2/`). Final original-1174-plus-new-regression evidence,
JUnit, exact commands and same-snapshot manifests are in `semantic-scope-final/`.
